# AI Advent — День 3, День 4 и День 5

Задача «AI Advent Challenge». Приложение — учебный стенд из трёх вкладок:

- **День 3 — Разные способы рассуждения**: одна и та же задача решается моделью
  четырьмя разными способами рассуждения, а затем LLM-as-a-judge оценивает,
  какой способ дал лучший результат: выставляет оценки и определяет порядок мест.
  **Все четыре способа и судья выполняются с одной и той же температурой**
  (по умолчанию `0.5`) — разница в качестве объясняется только структурой контекста.
- **День 4 — Температура**: матрица «4 типа задач × 3 температуры» —
  техническая, творческая, логическая и аналитическая задачи, каждая
  выполняется при `temperature = 0`, `0.7` и `1.2` (12 параллельных вызовов);
  ответы сравниваются по точности, креативности и разнообразию, а LLM
  формулирует вывод — для каких типов задач какая настройка подходит.
  Дефолтные задания — расширенный пул вариантов (10–20) с запретом банальных
  ходов; уроки прогона — в разделе
  «Выводы эксперимента (День 4)».
- **День 5 — Версии моделей**: поэтапный бенчмарк трёх моделей gpustack
  разного уровня — слабой (`qwen3.8-27b`), средней (`deepseek-v4-flash`) и
  сильной (`glm-5.3-flash`). Три задачи возрастающей сложности (простая,
  средняя, сложная) выполняются по очереди, внутри этапа модели отвечают
  параллельно (9 вызовов). Замеряются время ответа, число сгенерированных
  токенов и стоимость (для внутреннего шлюза — бесплатно); картина
  наполняется пошагово, а в конце LLM-аналитик собирает итоговое
  сравнение: качество по этапам, скорость, ресурсоёмкость и рекомендации,
  для каких задач какая модель подходит.

Бэкенд — FastAPI + uvicorn, обращения к LLM — через официальную библиотеку
`openai`. Фронтенд — одностраничное приложение (тёмная тема) в папке `static/`.

## Возможности

- **4 способа рассуждения**, каждый решает одно и то же задание:
  - `direct` — прямой ответ одной моделью;
  - `step_by_step` — system-промпт, требующий пошагового хода рассуждений;
  - `self_prompt` — модель сначала составляет «идеальный промпт», затем решает
    задачу этим промптом (2 вызова);
  - `experts` — «консилиум» из трёх ролей: аналитик, инженер, критик (3 вызова,
    ответы склеиваются с заголовками ролей).
- **Параллельное решение**: четыре способа запускаются одновременно, общее
  время = самому медленному способу. Фронтенд опрашивает `GET /api/progress`
  и показывает статус каждого: готово (✓), решается (●), ожидание (○).
- **LLM-as-a-judge** — пятый вызов оценивает четыре решения и возвращает
  строгий JSON `{"winner", "scores", "solved", "ranking", "criteria", "rationale"}`,
  где `ranking` — все четыре метода в порядке от лучшего к худшему (места
  1–4), `criteria` — оценки каждого метода по пяти критериям
  (correctness, completeness, reasoning, efficiency — экономность
  по числу израсходованных токенов, speed — скорость по времени
  выполнения), из которых фронтенд
  рисует диаграммы в вердикте, а `solved` — решена ли задача каждым
  способом (true/false) по мнению судьи.
- **Бейджи на карточках**: пока судья думает — временный пульсирующий бейдж
  «судья выносит вердикт»; после вердикта каждая карточка способа получает
  метку «1-е место» … «4-е место» по ранжированию судьи и метку
  «задача решена» / «задача не решена» по флагам `solved`. В секции
  вердикта в это время крутится спиннер.
- **Своя задача** (свободный текст) — работает так же, как встроенные.
- **Устойчивость судьи**: снимается ```json-обёртка, 1 ретрай при невалидном
  JSON, иначе — HTTP 502. Если в ответе судьи нет `ranking`, порядок
  восстанавливается по убыванию оценок.
- **Вкладки День 3 / День 4 / День 5**: переключение без перезагрузки
  страницы; выбор модели общий и действует на все запросы вкладок Дней 3
  и 4 (в Дне 5 модели фиксированы — сравниваются уровни).
- **День 4, матрица температур**: четыре редактируемых задания (техническая,
  творческая, логическая, аналитическая) × t = 0 / 0.7 / 1.2 = 12 параллельных
  вызовов. Пока вызовы идут, фронтенд опрашивает
  `GET /api/temperature-progress` и рисует матрицу прогресса 4×3 со статусом
  каждой ячейки (✓ готово / ● выполняется / ○ ожидание) — как прогресс
  способов в Дне 3. Когда все 12 ответов собраны и работает аналитик,
  показывается фаза «Формирую вывод» с анимацией и скелетоном в блоке
  анализа. Когда матрица собрана, ответы показываются группами
  по типу задачи (по три карточки-температуры с токенами, временем и
  finish_reason), а вывод аналитика приходит вместе с результатами:
  что показал эксперимент и рекомендации по каждому типу задач.
- **День 5, поэтапный бенчмарк моделей**: три задачи возрастающей сложности
  (простая / средняя / сложная) выполняются по очереди, внутри этапа три
  модели gpustack — слабая (`qwen3.8-27b`), средняя (`deepseek-v4-flash`) и
  сильная (`glm-5.3-flash`) — отвечают параллельно (ThreadPoolExecutor):
  3 этапа × 3 модели = 9 вызовов. Прогресс-матрица «этапы × модели»
  (✓ / ● / ○) опрашивается через `GET /api/models-progress`, который отдаёт
  и частичные результаты: карточки завершённых этапов появляются на странице
  один за другим, ещё до конца бенчмарка. Когда все 9 ответов собраны,
  работает аналитик — фаза «Формирую вывод» — и приходит итоговая
  сравнительная картина: качество по этапам (где уровни сравнялись, где
  расходятся), скорость и ресурсоёмкость по сводным числам, вердикт «что
  даёт переход на модель уровнем выше» и рекомендации по задачам. Ячейки
  идут с общим системным промптом «по существу», температурой 0, лимитом
  6000 токенов и таймаутом 180 с — как ячейки матрицы Дня 4; анализ — без
  лимита токенов. Стоимость: все три модели внутреннего шлюза бесплатны
  (структура `MODEL_PRICING` готова под платные).

## Выводы эксперимента (День 4)

Первые прогоны (нейминг-задача и короткие задания, по одному запросу на каждую
температуру) показали:

- **Температура сама по себе не гарантирует новизны.** Для коротких
  нейминг-задач модель при любой из трёх настроек может тянуться к одним и тем
  же очевидным ходам. Эффективнее запрашивать расширенный пул вариантов
  (10–20) с последующим отбором или явно запрещать очевидные решения в
  промпте — поэтому дефолтные задания вкладки просят пул из 10 вариантов и
  запрещают банальные ходы (запрещённые случаи для технической задачи,
  запрещённые названия для творческой).
- **Один прогон на температуру — статистически ненадёжная выборка.** Любые
  выводы из такого прогона — гипотезы: для строгих выводов нужно несколько
  запусков на каждую настройку. Поэтому вкладка прогоняет четыре разных
  типа задач и просит аналитика формулировать рекомендации как гипотезы.

Эти уроки встроены в дефолтное задание вкладки (пул вариантов + запрет
банальных ходов).

## API

### `GET /api/tasks`

Список встроенных задач.

```json
{
  "tasks": [
    {
      "id": "wolf_goat_cabbage",
      "title": "Волк, коза и капуста",
      "kind": "logic",
      "description": "Крестьянин должен переправить через реку..."
    }
  ]
}
```

### `POST /api/solve`

Решает задачу четырьмя способами.

Тело запроса: `task_id` **или** `text`, плюс опционально `model` (имя модели из
белого списка `GET /api/models`; если не задано — модель из настроек),
`temperature` (0–1, по
умолчанию `0.5`) и `max_tokens` (1–10000, по умолчанию `2000`) — общий бюджет
completion-токенов на способ, суммарно на все его вызовы. Каждый следующий
вызов способа получает остаток бюджета: например, у `self_prompt` лимит 1000,
первый вызов израсходовал 300 — второй получает лимит 700; у `experts` три
вызова делят бюджет последовательно. Если бюджет исчерпан, оставшиеся вызовы
способа пропускаются (в ответе — пометка «лимит токенов исчерпан»).

```json
{
  "task_id": "counterfeit_coin",
  "model": "deepseek-v4-flash",
  "temperature": 0.5,
  "max_tokens": 2000
}
```

Ответ: для каждого способа — полный ответ и метаданные. Признак «задача
решена» определяется только судьёй (см. `/api/judge`) и появляется
на карточках после вердикта.

```json
{
  "task": { "id": "counterfeit_coin", "title": "Фальшивая монета" },
  "solutions": [
    {
      "method": "direct",
      "content": "Полный текст ответа...",
      "finish_reason": "stop",
      "completion_tokens": 120,
      "elapsed_ms": 540
    },
    {
      "method": "step_by_step",
      "...": "..."
    },
    {
      "method": "self_prompt",
      "...": "...",
      "prompt": "Полный промпт первого вызова...",
      "generated_prompt": "Сгенерированный моделью промпт..."
    },
    {
      "method": "experts",
      "content": "### аналитик\n...\n\n### инженер\n...\n\n### критик\n..."
    }
  ]
}
```

### `POST /api/judge`

LLM-as-a-judge оценивает переданные решения.

Тело запроса: источник задачи (`task_id`/`text`), опционально `model`
(модель судьи — обычно та же, что выбрана для способов) и массив `solutions`
(обычно — то, что вернул `/api/solve`, включая `completion_tokens` и
`elapsed_ms`: судья учитывает их в критериях efficiency — экономность
и speed — скорость). Поля `temperature` и `max_tokens`
судья игнорирует: он всегда работает с температурой `0` (максимально
детерминированный вердикт) и **без лимита токенов**, чтобы его JSON-ответ
не обрезался ни при каких настройках способов.

```json
{
  "task_id": "counterfeit_coin",
  "solutions": [
    { "method": "direct", "content": "..." },
    { "method": "step_by_step", "content": "..." }
  ]
}
```

Ответ:

```json
{
  "winner": "self_prompt",
  "scores": { "direct": 8, "step_by_step": 9, "self_prompt": 10, "experts": 9 },
  "solved": { "direct": false, "step_by_step": true, "self_prompt": true, "experts": false },
  "ranking": ["self_prompt", "step_by_step", "experts", "direct"],
  "criteria": {
"direct": { "correctness": 9, "completeness": 7, "reasoning": 8, "efficiency": 8, "speed": 9 },
"step_by_step": { "correctness": 9, "completeness": 9, "reasoning": 9, "efficiency": 7, "speed": 8 },
"self_prompt": { "correctness": 10, "completeness": 10, "reasoning": 10, "efficiency": 4, "speed": 6 },
"experts": { "correctness": 9, "completeness": 9, "reasoning": 8, "efficiency": 3, "speed": 4 }
  },
  "rationale": "Краткое обоснование судьи...",
  "retries": 0,
  "prompt": "[system] ...\n\n[user] Задача: ...\n\nРешения: ...",
  "retry_prompt": "[system] ... (присутствует только если был ретрай)"
}
```

`ranking` — методы в порядке убывания качества; фронтенд использует его для
меток «1-е место» … «4-е место» на карточках. `solved` — решена ли задача
каждым способом по мнению судьи (true — только если дан правильный итоговый
ответ, даже если решение неполное); фронтенд показывает это бейджем
«задача решена / задача не решена». `criteria` — оценки по критериям
correctness (корректность), completeness (полнота), reasoning (обоснованность),
efficiency (экономность — чем меньше completion-токенов израсходовано, тем выше),
speed (скорость — чем меньше время выполнения, тем выше), шкала 0–10. В вердикте сначала идёт текстовое обоснование,
затем одна общая диаграмма: строки — критерии, внутри каждой — полоска каждого
способа своим цветом; завершает диаграмму строка «Итог» с итоговыми баллами.
Легенда связывает цвет со способом, его местом и итоговым баллом. Если судья не
вернул разбивку, каждый критерий принимается равным итоговой оценке метода.

Лимит токенов и температура из запроса к `/api/solve` управляют только
способами рассуждения. Судья всегда вызывается с температурой `0` и без
ограничения токенов.

### `POST /api/temp-matrix`

День 4: матрица «4 типа задач × 3 температуры». Четыре задания (техническая,
творческая, логическая, аналитическая) выполняются на одной модели при
температурах `0`, `0.7` и `1.2` — 12 параллельных вызовов (ThreadPoolExecutor,
как способы в `/api/solve`), после чего аналитик сравнивает всю матрицу и
формулирует вывод. Анализ приходит в том же ответе.

Тело запроса: `queries` — словарь `{"technical": "...", "creative": "...",
"logical": "...", "analytical": "..."}` (пустые или отсутствующие значения
заменяются дефолтными из `tasks.TEMP_TASKS`) и опционально `model` (имя из
белого списка; если не задано — модель из настроек). Ячейки идут с общим
системным промптом «по существу, ровно столько пунктов, сколько запрошено» —
без него reasoning-фаза GLM на открытых задачах раздувает генерацию в разы
(до таймаутов на t=1.2), а в ответ лезут черновики. Плюс страховка: лимит
6000 токенов и таймаут 180 с на ячейку. Анализ, как и раньше, без лимита
токенов.

Пока вызовы выполняются, фронтенд опрашивает `GET /api/temperature-progress`
— статусы текущего запуска по аналогии с `GET /api/progress` в Дне 3:
`{"done": ["technical:0.0", "creative:0.7"], "running": ["logical:1.2"],
"total": 12}` — идентификатор ячейки «`<тип>:<температура>`» (`done` — ответ
получен, `running` — выполняется сейчас).

```json
{
  "queries": {
    "technical": "Придумай 10 краевых случаев для функции apply_discount(cart, promo_code), которая применяет промокод к корзине интернет-магазина. Запрещены очевидные случаи: «пустая корзина», «неверный промокод», «истёкший промокод». К каждому — однострочное описание ожидаемого результата.",
    "creative": "Придумай 5 названий для панк-группы, которая играет колыбельные...",
    "logical": "На столе горело семь свечей. Три задули...",
    "analytical": "Поддержка получила за неделю 40 жалоб..."
  },
  "model": "deepseek-v4-flash"
}
```

Ответ: ответы группируются по типу задачи, ключи температур — строки
(`"0.0"`, `"0.7"`, `"1.2"`); метаданные те же, что у решений `/api/solve`
(вместо `method` — `temperature`).

```json
{
  "results": {
    "technical": {
      "0.0": {
        "temperature": 0,
        "content": "Полный текст ответа...",
        "finish_reason": "stop",
        "completion_tokens": 120,
        "elapsed_ms": 540
      },
      "0.7": { "...": "..." },
      "1.2": { "...": "..." }
    },
    "creative": { "...": "..." },
    "logical": { "...": "..." },
    "analytical": { "...": "..." }
  },
  "analysis": "Markdown-вывод: что показал эксперимент, рекомендации по типам задач, ограничения эксперимента.",
  "prompt": "[system] ...\n\n[user] Матрица результатов (4 типа задач × температуры 0/0.7/1.2): ..."
}
```

Аналитик всегда вызывается с температурой `0` и без лимита токенов, чтобы
Markdown-вывод не обрезался. В его вывод по промпту входят разделы
«Что показал эксперимент» и «Рекомендации по типам задач» (по строке на
каждый из четырёх типов).

### `POST /api/models-bench`

День 5: поэтапный бенчмарк трёх моделей. Три задачи возрастающей сложности
(простая, средняя, сложная — дефолты в `tasks.BENCH_STAGES`) выполняются
по очереди, внутри этапа три модели — слабая `qwen3.8-27b`, средняя
`deepseek-v4-flash`, сильная `glm-5.3-flash` (список в
`main.MODEL_BENCH_TIERS`) — отвечают параллельно (ThreadPoolExecutor):
9 вызовов. Системный промпт и температура (0) одинаковы для всех —
сравнение уровней честное. Лимит 6000 токенов и таймаут 180 с на ячейку.
Когда все этапы собраны, аналитик (t=0, без лимита токенов) строит итоговое
сравнение по сводным замерам (суммарное время и токены каждой модели).

Тело запроса: `queries` — словарь `{"simple": "...", "medium": "...",
"hard": "..."}` (пустые или отсутствующие значения заменяются дефолтными
из `tasks.BENCH_STAGES`).

```json
{
  "queries": {
    "simple": "Одним абзацем объясни, зачем в коде нужны тесты.",
    "medium": "Напиши на Python функцию is_balanced(s)...",
    "hard": "Команда из трёх разработчиков спорит..."
  }
}
```

Ответ: результаты сгруппированы по этапам, внутри этапа — по уровню модели
(`weak` / `medium` / `strong`); метаданные ячейки — модель, бейдж-уровень,
ответ, `finish_reason`, токены, время и `price_per_million` (для внутреннего
шлюза — `null`, фронтенд показывает «бесплатно (шлюз)»).

```json
{
  "results": {
    "simple": {
      "weak":   { "model": "qwen3.8-27b", "label": "Слабая", "content": "...", "finish_reason": "stop", "completion_tokens": 444, "elapsed_ms": 4479, "price_per_million": null },
      "medium": { "...": "..." },
      "strong": { "...": "..." }
    },
    "medium": { "...": "..." },
    "hard": { "...": "..." }
  },
  "analysis": "Markdown: качество по этапам, скорость и ресурсоёмкость, итоговая сравнительная картина, рекомендации.",
  "prompt": "[system] ...\n\n[user] Поэтапный бенчмарк... Сводные замеры: ...",
  "queries": { "simple": "...", "medium": "...", "hard": "..." }
}
```

В вывод аналитика по промпту входят разделы «Качество ответов по этапам»,
«Скорость и ресурсоёмкость», «Итоговая сравнительная картина»
(что даёт переход на модель уровнем выше) и «Рекомендации» (по строке на
каждую модель).

### `GET /api/models-progress`

Прогресс текущего бенчмарка Дня 5 — по аналогии с
`GET /api/temperature-progress`. Идентификатор ячейки —
«`<этап>:<уровень>`» (`"simple:weak"`). Помимо статусов отдаёт
`results` — завершённые этапы с полными ответами: фронтенд показывает
карточки этапов пошагово, не дожидаясь конца бенчмарка.

```json
{
  "done": ["simple:weak", "simple:medium", "simple:strong"],
  "running": ["medium:weak", "medium:medium", "medium:strong"],
  "total": 9,
  "results": {
    "simple": { "weak": { "...": "..." }, "medium": { "...": "..." }, "strong": { "...": "..." } }
  }
}
```

### Коды ошибок

| HTTP | Случай |
|---|---|
| `400` | Не передан `task_id`/`text`, нет `solutions`, `temperature` вне 0–1 или неизвестная модель |
| `404` | Неизвестный `task_id` |
| `502` | Ошибка сети/LLM, или судья не вернул валидный JSON после ретрая |
