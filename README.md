# День 3 — Разные способы рассуждения

Задача «AI Advent Challenge»: одна и та же задача решается моделью четырьмя
разными способами рассуждения, а затем LLM-as-a-judge оценивает, какой способ
дал лучший результат: выставляет оценки и определяет порядок мест.
**Все четыре способа и судья выполняются с одной и той же температурой**
(по умолчанию `0.5`) — разница в качестве объясняется только структурой контекста.

Бэкенд — FastAPI + uvicorn, обращения к LLM — через официальную библиотеку
`openai`. Фронтенд — одностраничное приложение (тёмная тема) в папке `static/`.

---

## Возможности

- **4 способа рассуждения**, каждый решает одно и то же задание:
  - `direct` — прямой ответ одной моделью;
  - `step_by_step` — system-промпт, требующий пошагового хода рассуждений;
  - `self_prompt` — модель сначала составляет «идеальный промпт», затем решает
    задачу этим промптом (2 вызова);
  - `experts` — «консилиум» из трёх ролей: аналитик, инженер, критик (3 вызова,
    ответы склеиваются с заголовками ролей).
- **Параллельное решение**: четыре способа запускаются одновременно, общее
  время = самому медленному способу. Фронтенд опрашивает `GET /api/progress`
  и показывает статус каждого: готово (✓), решается (●), ожидание (○).
- **LLM-as-a-judge** — пятый вызов оценивает четыре решения и возвращает
  строгий JSON `{"winner", "scores", "solved", "ranking", "criteria", "rationale"}`,
  где `ranking` — все четыре метода в порядке от лучшего к худшему (места
  1–4), `criteria` — оценки каждого метода по пяти критериям
  (correctness, completeness, reasoning, efficiency — экономность
  по числу израсходованных токенов, speed — скорость по времени
  выполнения), из которых фронтенд
  рисует диаграммы в вердикте, а `solved` — решена ли задача каждым
  способом (true/false) по мнению судьи.
- **Бейджи на карточках**: пока судья думает — временный пульсирующий бейдж
  «судья выносит вердикт»; после вердикта каждая карточка способа получает
  метку «1-е место» … «4-е место» по ранжированию судьи и метку
  «задача решена» / «задача не решена» по флагам `solved`. В секции
  вердикта в это время крутится спиннер.
- **Своя задача** (свободный текст) — работает так же, как встроенные.
- **Устойчивость судьи**: снимается ```json-обёртка, 1 ретрай при невалидном
  JSON, иначе — HTTP 502. Если в ответе судьи нет `ranking`, порядок
  восстанавливается по убыванию оценок.

## Установка и запуск

```bash
# 1. Создайте виртуальное окружение и установите зависимости
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt

# 2. Настройте окружение
copy .env.example .env
#    откройте .env и укажите OPENAI_API_KEY (+ при необходимости OPENAI_MODEL, OPENAI_BASE_URL)

# 3. Запустите сервер
python -X utf8 -m uvicorn main:app --host 127.0.0.1 --port 8000
```

Откройте в браузере http://127.0.0.1:8000

### Переменные окружения (`.env`)

| Переменная | По умолчанию | Описание |
|---|---|---|
| `OPENAI_API_KEY` | — (обязательна) | Ключ API. |
| `OPENAI_MODEL` | `deepseek-v4-flash` | Имя модели. |
| `OPENAI_BASE_URL` | — | Базовый URL API (для OpenAI-совместимых прокси/LLM). |

## API

### `GET /api/tasks`

Список встроенных задач.

```json
{
  "tasks": [
    {
      "id": "wolf_goat_cabbage",
      "title": "Волк, коза и капуста",
      "kind": "logic",
      "description": "Крестьянин должен переправить через реку..."
    }
  ]
}
```

### `POST /api/solve`

Решает задачу четырьмя способами.

Тело запроса: `task_id` **или** `text`, плюс опционально `model` (имя модели из
белого списка `GET /api/models`; если не задано — модель из настроек),
`temperature` (0–1, по
умолчанию `0.5`) и `max_tokens` (1–10000, по умолчанию `2000`) — общий бюджет
completion-токенов на способ, суммарно на все его вызовы. Каждый следующий
вызов способа получает остаток бюджета: например, у `self_prompt` лимит 1000,
первый вызов израсходовал 300 — второй получает лимит 700; у `experts` три
вызова делят бюджет последовательно. Если бюджет исчерпан, оставшиеся вызовы
способа пропускаются (в ответе — пометка «лимит токенов исчерпан»).

```json
{
  "task_id": "counterfeit_coin",
  "model": "deepseek-v4-flash",
  "temperature": 0.5,
  "max_tokens": 2000
}
```

Ответ: для каждого способа — полный ответ и метаданные. Признак «задача
решена» определяется только судьёй (см. `/api/judge`) и появляется
на карточках после вердикта.

```json
{
  "task": { "id": "counterfeit_coin", "title": "Фальшивая монета" },
  "solutions": [
    {
      "method": "direct",
      "content": "Полный текст ответа...",
      "finish_reason": "stop",
      "completion_tokens": 120,
      "elapsed_ms": 540
    },
    {
      "method": "step_by_step",
      "...": "..."
    },
    {
      "method": "self_prompt",
      "...": "...",
      "prompt": "Полный промпт первого вызова...",
      "generated_prompt": "Сгенерированный моделью промпт..."
    },
    {
      "method": "experts",
      "content": "### аналитик\n...\n\n### инженер\n...\n\n### критик\n..."
    }
  ]
}
```

### `POST /api/judge`

LLM-as-a-judge оценивает переданные решения.

Тело запроса: источник задачи (`task_id`/`text`), опционально `model`
(модель судьи — обычно та же, что выбрана для способов) и массив `solutions`
(обычно — то, что вернул `/api/solve`, включая `completion_tokens` и
`elapsed_ms`: судья учитывает их в критериях efficiency — экономность
и speed — скорость). Поля `temperature` и `max_tokens`
судья игнорирует: он всегда работает с температурой `0` (максимально
детерминированный вердикт) и **без лимита токенов**, чтобы его JSON-ответ
не обрезался ни при каких настройках способов.

```json
{
  "task_id": "counterfeit_coin",
  "solutions": [
    { "method": "direct", "content": "..." },
    { "method": "step_by_step", "content": "..." }
  ]
}
```

Ответ:

```json
{
  "winner": "self_prompt",
  "scores": { "direct": 8, "step_by_step": 9, "self_prompt": 10, "experts": 9 },
  "solved": { "direct": false, "step_by_step": true, "self_prompt": true, "experts": false },
  "ranking": ["self_prompt", "step_by_step", "experts", "direct"],
  "criteria": {
"direct": { "correctness": 9, "completeness": 7, "reasoning": 8, "efficiency": 8, "speed": 9 },
"step_by_step": { "correctness": 9, "completeness": 9, "reasoning": 9, "efficiency": 7, "speed": 8 },
"self_prompt": { "correctness": 10, "completeness": 10, "reasoning": 10, "efficiency": 4, "speed": 6 },
"experts": { "correctness": 9, "completeness": 9, "reasoning": 8, "efficiency": 3, "speed": 4 }
  },
  "rationale": "Краткое обоснование судьи...",
  "retries": 0,
  "prompt": "[system] ...\n\n[user] Задача: ...\n\nРешения: ...",
  "retry_prompt": "[system] ... (присутствует только если был ретрай)"
}
```

`ranking` — методы в порядке убывания качества; фронтенд использует его для
меток «1-е место» … «4-е место» на карточках. `solved` — решена ли задача
каждым способом по мнению судьи (true — только если дан правильный итоговый
ответ, даже если решение неполное); фронтенд показывает это бейджем
«задача решена / задача не решена». `criteria` — оценки по критериям
correctness (корректность), completeness (полнота), reasoning (обоснованность),
efficiency (экономность — чем меньше completion-токенов израсходовано, тем выше),
speed (скорость — чем меньше время выполнения, тем выше), шкала 0–10. В вердикте сначала идёт текстовое обоснование,
затем одна общая диаграмма: строки — критерии, внутри каждой — полоска каждого
способа своим цветом; завершает диаграмму строка «Итог» с итоговыми баллами.
Легенда связывает цвет со способом, его местом и итоговым баллом. Если судья не
вернул разбивку, каждый критерий принимается равным итоговой оценке метода.

Лимит токенов и температура из запроса к `/api/solve` управляют только
способами рассуждения. Судья всегда вызывается с температурой `0` и без
ограничения токенов.

### Коды ошибок

| HTTP | Случай |
|---|---|
| `400` | Не передан `task_id`/`text`, нет `solutions`, или `temperature` вне 0–1 |
| `404` | Неизвестный `task_id` |
| `502` | Ошибка сети/LLM, или судья не вернул валидный JSON после ретрая |
